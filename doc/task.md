# task

## Постановка задачи и проектирование системы

### 1. Общая идея проекта

В рамках проекта реализована ML-система для обработки потоковых табличных данных на примере страхового датасета

Система должна:
- принимать данные батчами;
- сохранять новые порции данных;
- проверять качество каждого батча;
- очищать данные;
- выбирать лучшую модель;
- использовать её для предсказаний на новых данных;
- формировать summary-отчёт по истории работы системы.

---

### 2. Источник данных

В проекте используется датасет **Ethiopian Insurance Corporation** по страхованию транспортных средств за 2014–2018 годы.

Основные характеристики датасета:
- формат хранения исходных данных - CSV;
- в репозитории датасет хранится в архиве `motor_data14-2018.zip`;
- после подготовки используется исходный файл в директории `data/source/`;
- данные содержат временную переменную `INSR_BEGIN`, которая используется для разбиения на батчи;
- целевая переменная формируется на основе поля `CLAIM_PAID`. Если была выплата по страховке, объект относится к положительному классу, иначе - к отрицательному.

Из-за природы задачи классы получаются несбалансированными: страховые случаи встречаются реже, чем отсутствие выплат.

---

### 3. Прогнозируемая задача

В проекте решается задача **бинарной классификации**.
Цель модели - определить, относится ли запись к группе с повышенной вероятностью страхового случая.  
Иными словами, система должна предсказать факт наличия страховой выплаты по набору признаков клиента, полиса и объекта страхования.

---

### 4. Организация потоковой обработки данных
1. исходный датасет сортируется по времени;
2. данные разбиваются на месячные батчи;
3. батчи сохраняются отдельно;
4. при каждом запуске режима `update` система обрабатывает следующий батч.

В текущей структуре проекта для этого используются:
- `data/batches/` - подготовленные батчи;
- `data/raw_storage/` - сырые, уже поступившие в систему батчи;
- `data/clean_storage/` - очищенные батчи и накопленное хранилище данных

Состояние обработки батчей сохраняется отдельно, чтобы система понимала, какой батч уже был обработан, а какой должен идти следующим.

---

### 5. Контроль качества данных (Data Quality)

Для каждого нового батча система рассчитывает базовые показатели качества данных.

Простые проверки на корректность значений, например ограничения на допустимые диапазоны или условия вида “значение должно быть неотрицательным”.

#### Динамические правила
Дополнительно в проекте используются ассоциативные правила (Apriori).  
На первом батче строятся наиболее уверенные правила, а на следующих батчах система смотрит, насколько новые данные им соответствуют. Это помогает отслеживать нетипичные сочетания признаков и нарушения привычной структуры данных.

Метрики качества по батчам сохраняются отдельно, чтобы можно было потом анализировать их в динамике.

---

### 6. Очистка данных

После оценки качества батч проходит базовую очистку.

В проекте используются простые и понятные правила очистки:
- удаление строк с очень большим количеством пропусков;
- отбрасывание строк, которые нарушают допустимые статические правила;
- базовая нормализация структуры данных перед передачей в модель.

---

### 7. Подготовка признаков

#### Категориальные признаки
Для них применяется:
- кодирование через `OneHotEncoder` с поддержкой неизвестных категорий.

---

### 8. Проектирование моделей

В проекте рассматриваются две модели:

1. модель на деревьях решений;
2. нейронная сеть (`MLP`).

#### 8.1. Дерево решений
Для модели на деревьях используются заранее заданные гиперпараметры, например:
- `max_depth`;

#### 8.2. Нейронная сеть (`MLPClassifier`)
Для `MLPClassifier` используются гиперпараметры вида:
- `hidden_layer_sizes`;

---

### 9. Валидация и метрики

Часть данных текущего батча откладывается под валидацию, а на остальной части выполняется обучение.  
После этого для моделей считаются основные метрики бинарной классификации:

- precision;
- recall;
- f1-score;
- ROC-AUC.

В качестве основной метрики для выбора лучшей модели используется **f1-score**, так как задача несбалансированная, и простая accuracy здесь была бы не очень показательной.

---

### 10. Хранилище моделей и артефактов

В проекте предусмотрено сохранение основных артефактов ML-системы.

#### Что именно сохраняется
- батчи данных;
- сырые поступившие батчи;
- очищенные батчи;
- метрики качества данных;
- метрики моделей;
- сериализованные версии моделей;
- отчёты;
- результаты inference.

По текущей структуре репозитория основные артефакты лежат в:
- `artifacts/models/` - модели;
- `artifacts/metrics/` - метрики;
- `artifacts/reports/` - отчёты;
- `artifacts/predictions/` - результаты предсказаний.

Такое разделение помогает сделать проект более прозрачным: отдельно видно, что относится к данным, что - к моделям, а что - к аналитике работы системы.

---

### 11. Интерфейс запуска

Управление системой реализовано через `run.py`.

Основные команды:
- `python run.py -mode update` - обработка следующего батча, обновление данных и обучение моделей;
- `python run.py -mode inference -file <путь>` - применение лучшей модели к новым данным;
- `python run.py -mode summary` - построение итогового summary-отчёта.

Именно эти режимы описаны в текущем README проекта как основные пользовательские сценарии работы с системой.
---

### 12. Конфигурация проекта

Ключевые параметры системы вынесены в конфигурационный файл `config.json`.

Через него задаются:
- пути к данным и артефактам;
- настройки батчей;
- списки признаков;
- параметры data quality;
- параметры моделей.

### 14. CI/CD и GitHub Actions

Во второй части задания проект был доработан с помощью GitHub Actions.

Workflow проекта автоматически:
- поднимает окружение;
- устанавливает Python и зависимости;
- подготавливает данные;
- запускает обучение;
- строит summary;
- сохраняет логи и артефакты.

По структуре репозитория workflow-файлы действительно лежат в `.github/workflows/`, а сама папка уже присутствует в проекте.

Workflow можно запускать:
- при `push`;
- при `pull request`;
- вручную через интерфейс GitHub Actions.
